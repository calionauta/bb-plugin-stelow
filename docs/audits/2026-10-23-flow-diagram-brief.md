# P1: the flow diagram, derived from the catalog and proven renderable

**Type:** feature brief for a fresh-context agent. Load
`/skill:stelow-workflow-coding-standards` first (KISS, one owner per fact, fail
fast, file/function budgets).

**Base:** `origin/master`. Branch `feat/flow-diagram-2026-10-23` in your own
worktree. The shared checkout carries another thread's uncommitted work.

## Two decisions already made, and why

1. **The Mermaid text is the source of truth. The SVG is a derived cache.**
   Mermaid is versionable, diffable, portable, and re-renderable by any future
   pele. Do NOT treat the rendered SVG as the artifact of record. Emit and commit
   the `.mmd`; render it only to prove it renders.
2. **No new dependency.** Do not install `maid` or any Mermaid validator. The
   plugin already ships `pele` at an exact pin (`lib/diagram-strategy.mjs`,
   `PELE_PIN`), and the emitted Mermaid is generated by our own code, not written
   freehand by a model - so the renderer itself is the validator that matters.
   The test renders with pele and asserts a non-empty SVG.

## The job

Emit a Mermaid `flowchart` that describes the **real** workflow, derived from the
catalog - never hand-written beside it. A diagram drawn next to `stages.yaml`
instead of derived from it drifts, and a picture that lies about the flow is worse
than no picture.

Where the facts live (verify each against `origin/master`, do not trust this
brief blindly):

- `lib/transition-facts.mjs` already parses the vendored transition table into
  `{ stage: { targets: { next, accept, reject, rework, annotate } } }`, and
  `parseTransitionRows(text)` is the reader. `TRANSITION_KINDS` is the closed set.
- `lib/workflow-catalog.mjs` exposes `STAGE_TRANSITIONS` (the four MOVE verbs only)
  and `WORKFLOW_STAGES`. Read the comments there: `annotate` is deliberately not a
  move, so decide explicitly whether the diagram shows it, and say which and why.
- The table itself is `skills/stelow-workflow-orchestrator/references/transitions.md`
  (vendored, synced - read it, never edit it).

Deliver, in `lib/`:

- A pure emitter: `flowDiagramMermaid({ transitions, title? }) -> string`, plus a
  small `lib/diagram-model.mjs` if a normalised model makes it clearer. One owner
  per fact: the emitter takes parsed facts, it does not re-parse the table.
- Node ids must be stable and derived from the stage id (so a diff between two
  emitted diagrams is about the flow, not about layout).
- Edges carry the verb as the label. Terminal stages should be visibly terminal.
- Do NOT invent styling beyond what is needed to read it: no theme, no colours
  except a `classDef` for something the data actually distinguishes.

## Acceptance criteria (each must fail before the change)

1. **One edge per transition.** For the real table, the emitted Mermaid has exactly
   one edge per non-empty target row in `parseTransitionRows(transitions.md)`.
   Assert the count against the parser, not against a hardcoded number.
2. **Deleting a transition removes its edge.** Red proof: remove one row from a
   fixture copy of the table, re-emit, and show the edge count drop by exactly that
   row. Capture both numbers.
3. **It renders.** Pass the emitted source to the bundled pele renderer and assert
   a non-empty SVG (or HTML, depending on what pele's API returns - read
   `server/runtime/diagram-renderer.ts` and the `pele` package's exports first,
   and say which API you used in the record).
4. **No dead ends.** Every node has an inbound or outbound edge unless the data says
   it is a start/terminal; assert with the same rule `transition-facts` already
   uses, not a new one.

## Boundaries

- **Do not wire the UI or the RPC.** The modal and the artifact write path belong
  to another thread (`thr_ag6r95hn6q`); touching them here guarantees a conflict.
  Your deliverable is the emitter plus the render proof, nothing above `lib/`.
- No new dependency. No change to `skills/` or `data/stelow`. No push, merge, tag
  or release.
- Fresh worktree: `npm ci` (about 2 min) or symlink
  `/home/deploy/repos/bb-plugin-stelow/node_modules`, deleting the symlink before
  committing. An incomplete install gives a fake `Cannot find module 'pele'` at
  `server/runtime/platform.ts:145` - that is the install, not your change.
- Gates, all three, exit codes in the record: `npm run --silent typecheck`,
  `npm run --silent quality:shape`, `npm test`. Budgets are hard. A `.mjs` imported
  from TypeScript needs its `.d.mts` updated in the same commit.
